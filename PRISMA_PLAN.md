# Plan: Prisma, database and API for saving all tracker data

Status: **plan only, nothing implemented.** Items marked **DECISION** need your answer before Phase 1.

## 1. Where we are

- All user data lives in browser LocalStorage (`dsa-tracker:v1`, schema in `lib/storage.ts` / `Progress` in `lib/types.ts`).
- The 452 problems are static (`data/problems.json`). The schedule is **derived** (`generateSchedule(problems, startDate)`), never stored.
- Original constraint was "no backend, database or login". Saving to a database changes that, so this plan adds **identity (who owns the data)** as a first-class requirement.

What must be persisted (everything in `Progress` today):

| Today (`Progress`) | Becomes |
|---|---|
| `startDate` | `StudyPlan.startDate` |
| `completed[id] = {date, at}` | `ProblemProgress.completedAt` + `completedDate` |
| `notes[id]` | `ProblemProgress.note` |
| `revision[id]` | `ProblemProgress.revision` |
| `prefs.filters`, `prefs.celebratedMilestones` | `UserPreferences` |
| theme, sidebar collapsed | stay client-side (device preference, not account data) |

## 2. Decisions

| # | Decision | Recommendation | Why |
|---|---|---|---|
| D1 | Single user (just you) or accounts for many users | **Accounts**, with a **guest mode** that keeps working on LocalStorage | The schema costs the same either way; adding `userId` later means a painful migration. |
| D2 | Auth library | **Better Auth** or **Auth.js v5** (Prisma adapter) | Both support Next 16's `proxy.ts`. Auth.js needs a split config so the Prisma adapter stays out of the proxy; Better Auth documents the Next 16 proxy pattern directly. Pick one before Phase 2. Verify against the libraries' official docs, as my research came partly from blogs. |
| D3 | Database host | **Postgres on Neon** (via Vercel Marketplace) | Serverless-friendly, free tier, branching for preview deploys. Any Postgres works. |
| D4 | Seed `Problem` into the DB? | **Yes**, keep `data/problems.json` as the seed source | Enables foreign keys, integrity and future queries/admin. Seeding is idempotent (upsert by id). |
| D5 | Conflict policy for two devices | **Last write wins per problem** (by `updatedAt`) | Simple and predictable. The tracker has one writer at a time in practice. |
| D6 | Sign-in methods | Email magic link and/or Google/GitHub | Avoids storing passwords. |

## 3. Architecture

```
Client (TrackerProvider, optimistic)
   │  fetch JSON
   ▼
app/api/**/route.ts          thin: parse → auth → validate → call service → respond
   ▼
lib/server/services/*        business rules (progress, plan, import/export)
   ▼
lib/server/db.ts             PrismaClient singleton (driver adapter)
   ▼
Postgres
```

- **Route Handlers** are the public REST contract (testable, reusable by a future mobile app). Server Actions are not used for the same mutations, to avoid two code paths.
- **Data Access Layer**: `requireUser()` is the only way to learn the current user. The user id always comes from the session, **never from the request body**.
- **Validation**: zod schemas in `lib/server/schemas.ts`; the same schemas infer the client types.
- **Cache Components** (`cacheComponents: true`): API handlers are dynamic and uncached. Pages stay a static shell; the session read happens behind `<Suspense>` (per the bundled Next docs on authentication with Cache Components). Phase 1 keeps the existing client-side hydration (`ready` gate), so prerendering is unaffected.
- `proxy.ts` (Next 16's replacement for middleware) only does an optimistic cookie check/redirect. **Real authorization lives in every handler**, since the proxy does not protect API calls on its own.

## 4. Prisma models (draft)

> Prisma 7 specifics to confirm against the official Prisma v7 + Next.js guide before coding: `provider = "prisma-client"` with an explicit `output`, connection URL in `prisma.config.ts` (not the schema), a driver adapter (`@prisma/adapter-pg`, or Neon's adapter), and separate **pooled** (runtime) and **direct** (migrations) URLs.

```prisma
generator client {
  provider = "prisma-client"
  output   = "../lib/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

enum Difficulty     { EASY MEDIUM HARD }
enum RevisionStatus { NEEDS_REVISION MASTERED }

// --- Auth tables (User, Account, Session, Verification) are generated by the chosen auth library (D2).
//     Only the fields we depend on are shown.
model User {
  id          String       @id
  email       String       @unique
  name        String?
  createdAt   DateTime     @default(now())
  plan        StudyPlan?
  preferences UserPreferences?
  progress    ProblemProgress[]
}

// Seeded from data/problems.json. Stable id = "tuf-<takeuforward id>" so saved progress survives data refreshes.
model Problem {
  id              String     @id            // "tuf-401"
  order           Int        @unique        // 1..452, official sheet order (drives the schedule)
  title           String
  topic           String
  subtopic        String
  difficulty      Difficulty
  tier            String?                   // basic | core | pro (source of the difficulty mapping)
  url             String                    // primary practice link
  tufUrl          String
  leetcodeUrl     String?
  gfgUrl          String?
  solutionUrl     String?                   // C++ solution
  javaSolutionUrl String?
  progress        ProblemProgress[]

  @@index([topic])
}

// One per user. The schedule is derived from startDate + Problem.order, never stored,
// so ticking problems can never move the plan.
model StudyPlan {
  id           String   @id @default(cuid())
  userId       String   @unique
  user         User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  startDate    DateTime @db.Date            // default 2026-10-13
  perDay       Int      @default(2)
  sheetVersion String   @default("a2z-2026-10")
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}

// One row per (user, problem) that has any non-default state. Row deleted when all fields return to default.
model ProblemProgress {
  userId        String
  problemId     String
  user          User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  problem       Problem  @relation(fields: [problemId], references: [id], onDelete: Restrict)

  completedAt   DateTime?                   // instant of completion (recent-activity ordering)
  completedDate DateTime? @db.Date          // user's LOCAL calendar day (streaks), sent by the client
  revision      RevisionStatus?
  note          String?  @db.Text           // <= 5000 chars, enforced in zod

  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt         // used for last-write-wins

  @@id([userId, problemId])
  @@index([userId, completedDate])          // streaks / activity chart
  @@index([userId, revision])               // revision lists
}

model UserPreferences {
  userId                String   @id
  user                  User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  filters               Json                          // same shape as Filters in lib/types.ts
  celebratedMilestones  Int[]    @default([])
  updatedAt             DateTime @updatedAt
}

// Optional (Phase 6): append-only history so un-ticking never loses analytics.
model CompletionEvent {
  id        String   @id @default(cuid())
  userId    String
  problemId String
  kind      String                                      // COMPLETE | UNCOMPLETE
  localDate DateTime @db.Date
  at        DateTime @default(now())

  @@index([userId, at])
}
```

Design notes:
- **Derived data stays derived**: schedule, streaks, topic progress, milestones are computed by the existing pure code in `lib/` from `StudyPlan` + `ProblemProgress`. No denormalised counters to drift.
- **Local dates**: streaks depend on the user's calendar day. The client sends `localDate`; the server only accepts a value within ±1 day of server UTC (anti-abuse).
- `Problem` uses `Restrict` on delete, so a removed problem can't silently erase user history.

## 5. API contract (`app/api/v1/**`, JSON, all require a session unless noted)

| Method & path | Purpose | Body → Response |
|---|---|---|
| `GET /api/v1/progress` | Full snapshot to hydrate the app | → `{ plan, progress: {…}, prefs }` (same shape as today's `Progress`, so the client swap is small) |
| `PUT /api/v1/progress/:problemId` | Set any of completion / note / revision for one problem (idempotent) | `{ completed?: boolean, localDate?, note?: string \| null, revision?: "needs-revision" \| "mastered" \| null, clientUpdatedAt? }` → updated row; `409` with current row if the server copy is newer |
| `DELETE /api/v1/progress/:problemId` | Clear all state for one problem | → `204` |
| `PUT /api/v1/plan` | Change start date | `{ startDate }` → plan |
| `PATCH /api/v1/preferences` | Save filters / celebrated milestones | partial → preferences |
| `GET /api/v1/export` | Download JSON (same format as the current Export button) | → file |
| `POST /api/v1/import` | Replace or merge from a validated export | `{ mode: "replace" \| "merge", data }` → summary; reuses `validateProgress`; one transaction; size cap 5 MB |
| `DELETE /api/v1/progress` | Reset everything for the user | `{ confirm: "RESET" }` → `204` |
| `POST /api/v1/migrate/local` | One-time claim of guest LocalStorage data after first sign-in | same as import `merge`, newest `updatedAt` wins |
| `GET /api/health` (public) | Liveness + DB ping | → `{ ok: true }` |
| `/api/auth/[...all]` | Auth library routes | per library |

Conventions:
- Errors: `{ "error": { "code": "VALIDATION" | "UNAUTHENTICATED" | "NOT_FOUND" | "CONFLICT" | "RATE_LIMITED", "message": "…", "fields"?: {…} } }` with matching HTTP status (400/401/404/409/429).
- Mutations are idempotent; `PUT` can be retried safely (needed for offline retries).
- Responses are never cached (`Cache-Control: no-store`).
- Security: authz on every handler, `problemId` must exist, zod on every body, `Origin` check on mutations, SameSite cookies, rate limiting on mutation routes (Upstash or Vercel firewall), no PII in logs.

## 6. Client sync design (keeps today's instant UX)

1. `TrackerProvider` stays optimistic: the UI updates immediately from local state (unchanged logic).
2. Each change enqueues a write: `PUT /progress/:id`. Writes are debounced per problem (notes: 500 ms), retried with backoff, and flushed on `visibilitychange`/`pagehide`.
3. LocalStorage remains a **write-through cache**, so the app works offline and loads instantly; the server snapshot replaces it after `GET /progress`.
4. A small header indicator shows **Saved · Saving… · Offline (n pending)**.
5. **Guest mode** (no session): behaves exactly as today. After first sign-in, a dialog offers "Move my local progress to my account" → `POST /migrate/local`.
6. Feature flag `NEXT_PUBLIC_SYNC` lets us ship the backend dark and switch it on per environment.

## 9. Testing

- **Unit** (existing vitest): schemas, `validateProgress` reuse, date-window guard, service logic with a real Postgres test database (Neon branch or Docker) rather than mocks, so constraints are actually exercised.
- **Route tests**: call exported `GET/PUT/…` handlers with `Request` objects: 401 without session, 400 invalid body, 404 unknown `problemId`, 409 stale write, idempotent retry, cross-user isolation (user A can never read or write user B).
- **E2E smoke** (browser): sign in, tick, reload, tick on a second context.
- **CI**: `npm install` with no flags (the Vercel lesson), `prisma generate`, lint, type-check, tests, build.

## 10. Vercel / build notes

- Add `"postinstall": "prisma generate"` so the generated client exists on Vercel.
- Run migrations as a deliberate deploy step (`prisma migrate deploy` using the **direct** URL), not on every cold start.
- Env vars: `DATABASE_URL` (pooled), `DIRECT_URL`, auth secret, OAuth client ids/secrets. Preview deployments use a Neon branch.
- Keep Node ≥ 22.12 (already set in `package.json` `engines`).

## 11. Risks

| Risk | Mitigation |
|---|---|
| Adds accounts to an app that was deliberately login-free | Guest mode stays fully functional; sync is opt-in |
| Lost writes on flaky networks | Idempotent PUT + client queue + pending-count indicator |
| Streak wrong across time zones | Client-supplied local date, bounded by ±1 day of server UTC |
| Prisma 7 / Next 16 setup drift | Follow the official v7 + Next.js guide when implementing; pin versions; verify `prisma.config.ts` details |
| Problem list changes upstream | IDs are stable; seed upserts; `Restrict` delete protects history |
| Dual write paths (LocalStorage and DB) diverging | Single sync module; server snapshot is authoritative after load |
